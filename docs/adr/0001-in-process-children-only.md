# 0001. 子セッションは同一プロセス内のみ(非同期実行を持たない)

## 状態

採用

## 用語

ここでいう**非同期実行**は「親が子の完了を待たずに制御を戻すこと」を指す。複数の子が同時に動く
**並列実行**は含まない。本決定は並列実行を禁止せず、`spawn_agents` は実際に並列で動く。

## 文脈

`pi-subagents` は非同期実行を別プロセスの runner として実装している。この経路は同期版とは別のコードで
モデル指定・思考レベル・文脈を再構成し、JSON 経由で伝達する。upstream の CHANGELOG には
「async でモデル/思考レベルの指定が無視される」同種の修正が繰り返し記録されており、構造的に再発する。
実際に最新版(0.71.0)でもこの経路は二重実装のままである。

また、モデルのエージェントループにとって非同期実行は扱いにくい。結果の受け取りが依存関係の障壁と
切り離され、状態確認と再開の機構を要求するため、得られる並列性に対して複雑さが過大になる。

## 決定

子セッションは `createAgentSession` による同一プロセス内セッションのみとし、非同期実行・別プロセス
runner・run status ファイルを持たない。resume / revive は、それらを成立させるために必要だった
機構であり、同時に非目標とする(セッションは in-memory で、落ちたらやり直す)。

## 結果

- モデル解決は1経路だけになり、「指定したモデルが使われない」分岐が存在しなくなる。
- 兄弟セッションが同一ヒープ上にセッションオブジェクトとして並ぶため、`AgentSession.steer()` /
  `followUp()` を兄弟に対して直接呼べる。これが兄弟間メッセージングの成立条件である
  (別プロセスなら転送層が要る)。
- **呼び出し元は全子の完了を待つ**。長時間ジョブを投げて別の作業を続ける使い方はできず、
  応答時間は最も遅い子に律速される。これは受け入れるコストであり、長時間の作業は
  小さく分割して順に spawn する運用を前提にする。
- 親プロセスが落ちれば子も消える。耐障害性は持たないが、それは本拡張の目的ではない。

## 再検討の条件

「親を待たせずに子を走らせたい」という需要が実運用で確認され、かつ次のいずれかに該当する場合に
in-process のバックグラウンド子を検討する(別プロセス runner は選ばない)。

- 待ち時間が実測で問題になり、タスク分割では解消しない
- 子→親の質問(判断のエスカレーション)が必要になった
