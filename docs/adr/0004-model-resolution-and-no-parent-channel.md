# 0004. モデル解決を1経路に固定し、子→親のチャネルを持たない

## 状態

採用

## この ADR が1つである理由

2つの決定は独立ではなく、どちらも ADR 0001(同期・同一プロセスのみ)から導かれる。
非同期実行を持たないので親は子の完了を待ち、その間は親のモデルターンが停止する。その結果:

- モデルを解決する場所が1つ(起動時)しかなくなる → 決定1
- 親が応答できないので子→親の質問が成立せず、親が実行中の子に指示する時点も無い → 決定2

片方だけを見直すと他方が破綻するため、1つの決定記録として扱う。

## 文脈

競合実装の調査([research.md](../research.md))で次が確認できた。

- Claude Code の解決順は env `CLAUDE_CODE_SUBAGENT_MODEL` → 呼び出し時引数 → 定義 → 継承。
  呼び出し側の指定が定義に勝つ。
- Codex は役割設定を重ねた後、親ターンの実行時上書きを再適用する。これも「呼び出し側が勝つ」。
- opencode はネイティブでは呼び出し時にモデルを指定できず、定義 → 呼び出し元セッションの順。
  その順序を変える第三者プラグインが存在する。
- `pi-subagents` は非同期経路だけモデル解決が別実装になり、指定が無視される不具合を繰り返し出した。

また、同期 spawn では親のモデルターンがツール結果まで停止する。pi-subagents は子→親の質問を
pause/resume 機構で解いており、その機構が複雑さの主要因だった。

## 決定

1. モデル解決は `tasks[].model` → `agent 定義の model` → `親セッションの model` の1経路のみ。
   解決できない明示指定は**エラー**とし、黙って別のモデルに落とさない。
   env 変数によるグローバル上書きは設けない(YAGNI)。
2. `message_agent` に `to: "parent"` を設けない。子→親の質問、親→子の steering、
   pause/resume をすべて非目標とする。

## 結果

- 「指定したモデルが使われたか」は `spawn_agents` の `results[].model` を見れば必ず分かる。
  これはツール結果としてモデルに返るため、指定が無視された状態を黙認できない。
- 子同士の会話は成立する: 兄弟は各自のモデルループを持つ独立セッションとして並走し、
  親が停止していても互いに応答できる。`spawn_agents` を N 並列にした理由でもある。
- **失う機能**: 子は判断を仰げない。曖昧なタスクでは子が自分で決めるか、結果に未決として残す。
  呼び出し側はタスク文に判断基準を書く必要がある。

## 再検討の条件

- 子→親の質問: 子の判断ミスが実害を出し、かつ「タスク文に判断基準を書く」運用で防げなかった場合。
  最小解(in-process のバックグラウンド子)は [research.md](../research.md) の保留節にある。
- モデル解決の順序: Pi 側にグローバルな既定(subagent 用の既定モデル設定など)が入り、
  定義ごとの指定より優先したい需要が出た場合。
