# ADR 0002: 子が人間に質問できる `ask_user` ツール

- 状態: 廃止 (2026-09-26 削除)
- 日付: 2026-09-26
- 対象: 子に注入していた `ask_user` ツール

## 廃止の理由 (2026-09-26)

- 本来あるべき姿は子から**親エージェント**への質問。`ask_user` は人間という場を借りた代替手段で、
  そのためだけに対話 UI とダイアログの寿命に依存する結合を持ち込んでいた。
- ダイアログは単一スロットで、並行する `spawn_agents` 呼び出しをまたぐと後から出た側が先行側を置き換え、
  先行側は未解決のままハングする。中止時もダイアログは閉じず、タイムアウトが効かない。
- ツール面の予算を恒常的に消費する(52/400 トークン)割に、得られるのは利便性だけで代替可能。
- 削除した対象: `ask_user` ツール、`createAskQueue`、`SpawnContext.askUser`、子ツールの構成、
  関連テスト、README の記述。

## 背景

- 親モデルは `spawn_agents` の実行中で停止しているため、子の質問に答えられない。
- 実務で詰まるのは判断の曖昧さで、答えられるのは人間だけ。Claude Code も `AskUserQuestion` は人間向けであり、
  子から親モデルへの質問は非同期アーキテクチャでのみ成立する。
- 子は `message_agent` で兄弟としか話せず、人間に聞く手段が無い。

## 決定

1. 子ツール `ask_user({ question })` を追加する。質問は親セッションの `ctx.ui.input` で人間に届く。
2. 注入は `ctx.hasUI` が真のときだけ。print / JSON モードの子は `message_agent` だけを持つ。
3. 質問は spawn 呼び出し単位のキューで直列化する。同時に走る複数の子がダイアログを奪い合わない。
4. キャンセルまたは空回答は、「回答なし。仮定を明示して進めること」というガイダンスを返す。
5. 子のツール集合は `SpawnDependencies.childTools` に集約し、
   `message_agent` と `ask_user` の構成を1箇所で決める。

## 理由

- 子セッションの extension runner に `setUIContext` で親 UI を付ける方法は、
  UI の所有権が親子で二重になり、子の拡張が親の状態を触る経路を作る。
  親 ctx のダイアログをクロージャで子ツールに渡す方が副作用が小さい。
- TUI/RPC 以外に UI は無いので、
  存在しない能力をモデルに見せない(常時注入して失敗させるより 1 ターン無駄にしない)。
- 質問の直列化は UI 側の挙動に依存せず、pi-spawn で決定的にできる。

## 帰結

- `ask_user` は対話 UI があるときだけ子に渡る。ツール面の契約テストは両方の構成を確認する。
- ツール定義の合計が増えるため、`TOKEN_BUDGET` の実測値を更新する。
- 質問と回答は子のセッションに残る。親モデルは回答を知らないため、
  必要な内容は子の結果に含めさせる。
- タイムアウトや中止で親ターンが終わると、未回答のダイアログは子の停止に伴い破棄される。
  (実装後に判明: 実際は破棄されず、回答されるまで `spawn_agents` が待つ。上の「廃止の理由」を参照)

## 代替案

| 代替 | 却下理由 |
|---|---|
| `message_agent` の宛先に `user` を追加 | 「兄弟へのメッセージ」という概念に人間が混ざり、run id 解決と意味が衝突する |
| 常に `ask_user` を注入し、UI 無しでは失敗を返す | ヘッドレスの子が1ターン無駄にする。能力の有無をツール面で表す方が単純 |
| 子の extension runner に親 UI を `setUIContext` で付ける | 子の拡張が親 UI を操作でき、所有権と後始末が曖昧になる |
